1 0이 되는 원리 — "고치지 말고 다시 지어라"

핵심은 단순하다. 일반 베이스(python:3.13 등)는 OS·셸·패키지매니저·빌드도구가 잔뜩 들어있고 그게 전부 CVE 표면이다. 그걸 버리고, 앱 실행에 꼭 필요한 패키지만 Wolfi(매일 패치되는 컨테이너 전용 리눅스)에서 골라 새 이미지로 조립한다. CVE는 "제거"되는 게 아니라 애초에 존재하지 않게 된다.

trivy·grype 2종 스캐너 교차검증. 0을 만드는 건 재빌드이고, 스캐너는 확인만 한다.

④의 재빌드 루프 = melange/apko가 매번 packages.wolfi.dev의 최신 패키지를 받으므로, 새로 공개된 CVE의 패치를 다시 빌드만 해도 흡수한다. 이 루프를 scripts/harden.sh가 구현한다(아래).

harden.sh — "0 만드는" 로컬 파이프라인 (전체)

scripts/harden.sh#!/usr/bin/env bash
# 입력: 앱(go|python|java) · 출력: CVE 0이 검증된 이미지 / 안 되면 잔여 보고 후 실패
set -euo pipefail
APP="${1:?usage: scripts/harden.sh <go|python|java>}"
MAX_ROUNDS="${MAX_ROUNDS:-2}"
IMG="harden-${APP}:wolfi"

scan_count() {  # trivy로 HIGH/CRITICAL 개수만 추출
  trivy image -q --severity HIGH,CRITICAL --format json "$1" 2>/dev/null \
    | python3 -c 'import sys,json;d=json.load(sys.stdin);print(sum(len(r.get("Vulnerabilities") or []) for r in (d.get("Results") or [])))'
}

for round in $(seq 1 "$MAX_ROUNDS"); do
  # Wolfi 최신 패키지로 다시 짓기 → OS 보안패치 자동 반영
  make APP="$APP" image >/dev/null
  n=$(scan_count "$IMG")
  echo "   trivy HIGH/CRITICAL: $n"
  if [ "$n" -eq 0 ]; then
    grype "$IMG" -q -o json | # grype 교차검증 ...
    echo "✅ $IMG: CVE 0 (검증 완료)"; exit 0
  fi
  echo "⚠ 잔여 $n건 — 최신 패치로 재빌드 재시도"; trivy image -q --severity HIGH,CRITICAL "$IMG"
done
echo "❌ 잔여 CVE: 앱 의존성 bump 또는 Wolfi 패치 대기 필요"; exit 1
✅
./scripts/harden.sh go 실측 결과: trivy 0 · grype 0 · CVE 0 검증 완료. 입력 무엇이든 출력은 "0이 증명된 이미지" 또는 "왜 0이 안 되는지 명시한 실패".

3 레시피 파일 해부 — 진짜 알맹이

CI YAML은 껍데기다. 실제 하드닝은 이 두 종류의 레시피 파일이 한다. 언어마다 한 쌍씩 둔다.

① melange-<lang>.yaml — 소스를 "서명된 패키지"로

역할: 빌드 도구(컴파일러·pip·JDK)를 이 단계 안에서만 쓰고, 결과물 .apk 하나를 뱉는다. → 빌드 도구는 최종 이미지에 절대 안 따라간다.

melange-go.yamlpackage:
  name: hello
  version: 1.0.0
environment:           # ← 빌드 '환경' (여기서만 존재)
  contents:
    keyring:      [https://packages.wolfi.dev/os/wolfi-signing.rsa.pub]
    repositories: [https://packages.wolfi.dev/os]
    packages:     [busybox, ca-certificates-bundle, go]   # go 컴파일러 = 빌드용
pipeline:              # ← 빌드 단계 (go/build 내장 파이프라인)
  - uses: go/build
    with: { modroot: app-go, packages: ., output: hello }

언어별 pipeline 부분만 다르다:

언어빌드 도구 (environment)pipeline 핵심
Gogouses: go/build — 정적 바이너리
Pythonpython-3.13, py3.13-pippip install --target로 의존성을 패키지에 vendoring
Javaopenjdk-21-default-jdk, gradle-9gradle jar → jar를 /usr/share/app에 install
 
melange-python.yaml (pipeline 부분)pipeline:
  - runs: |
      SP="${{targets.destdir}}/usr/lib/python3.13/site-packages"
      mkdir -p "$SP" "${{targets.destdir}}/usr/bin"
      # requirements.txt 의존성을 패키지 안으로 직접 설치 (런타임 이미지엔 pip 불필요)
      python3.13 -m pip install --no-cache-dir --target="$SP" -r app-python/requirements.txt
      install -m644 app-python/main.py "${{targets.destdir}}/usr/bin/hello-py"

② apko-<lang>.yaml — 패키지를 "최소 이미지"로

역할: 여기 선언한 패키지만 이미지에 들어간다. Dockerfile·RUN·셸 없음. → 선언 안 한 건 이미지에 존재하지 않는다(= 셸도, 컴파일러도 없음).

apko-go.yamlcontents:
  keyring:
    - https://packages.wolfi.dev/os/wolfi-signing.rsa.pub
    - keys/melange.rsa.pub          # 내 melange 패키지 검증용 공개키
  repositories:
    - https://packages.wolfi.dev/os
    - '@local /work/packages'       # melange가 만든 로컬 패키지
  packages:
    - ca-certificates-bundle
    - hello@local                  # 내 앱. go 컴파일러는 없음!
accounts:                          # ← non-root 강제
  users:  [{ username: nonroot, uid: 65532, gid: 65532 }]
  run-as: 65532
entrypoint:
  command: /usr/bin/hello
☕
언어별 entrypoint 주의: Python은 python3.13 /usr/bin/hello-py, Java는 Wolfi JRE가 java를 PATH에 안 올려서 /usr/lib/jvm/java-21-openjdk/bin/java -jar ... 전체 경로 + JAVA_HOME env 지정.

왜 이 2단 구조가 0을 만드는가: melange(빌드) ↔ apko(런타임)를 물리적으로 분리하기 때문. 빌드에 필요한 무거운 도구는 melange environment에만 있고, apko contents에는 앱 실행 최소 패키지만 선언 → 런타임 이미지의 CVE 표면이 구조적으로 0에 수렴한다.

4 전체 워크플로 — 그대로 적용 (축약 없음)

아래가 완전한 .github/workflows/build.yml이다. 앞서 본 발췌가 아니라 13개 스텝 전부. 이 레포 구조(app-*/, melange-*.yaml, apko-*.yaml)와 함께 두면 커밋만으로 동작한다.

.github/workflows/build.yml (전체)name: build
on: { workflow_call: { inputs: {
  tag:       { type: string, required: true },
  extra_tag: { type: string, default: "" } } } }
permissions:
  contents: read
  packages: write        # GHCR push
  id-token: write        # cosign keyless OIDC (없으면 서명 실패)
jobs:
  build:
    runs-on: ubuntu-latest
    strategy: { fail-fast: false, matrix: { app: [go, python, java] } }
    steps:
      - uses: actions/checkout@v4
      - uses: sigstore/cosign-installer@v3
      - run: sudo apt-get update && sudo apt-get install -y skopeo
      - run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}-${{ matrix.app }}" >> "$GITHUB_ENV"
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }

      # ① melange: 서명키 생성 + 패키지 빌드
      - run: |
          docker run --rm -v "$PWD":/work -w /work cgr.dev/chainguard/melange:latest keygen keys/melange.rsa
          docker run --rm --privileged -v "$PWD":/work -w /work cgr.dev/chainguard/melange:latest \
            build "melange-${{ matrix.app }}.yaml" --arch x86_64 --signing-key keys/melange.rsa

      # ② apko: 이미지 조립 + SBOM
      - run: |
          mkdir -p sbom
          docker run --rm -v "$PWD":/work -w /work cgr.dev/chainguard/apko:latest \
            build "apko-${{ matrix.app }}.yaml" "${IMAGE}:${{ inputs.tag }}" /work/image.tar \
            --arch x86_64 --sbom-path /work/sbom

      # ③ CVE 게이트 — HIGH/CRIT 있으면 여기서 실패 → push 안 됨
      - uses: aquasecurity/trivy-action@0.28.0
        with: { input: image.tar, severity: HIGH,CRITICAL, exit-code: "1", ignore-unfixed: true }

      # ④ push (apko tar는 docker-archive 포맷) + digest 확보
      - run: |
          CRED="${{ github.actor }}:${{ secrets.GITHUB_TOKEN }}"
          skopeo copy docker-archive:image.tar "docker://${IMAGE}:${{ inputs.tag }}" --dest-creds "$CRED"
          [ -n "${{ inputs.extra_tag }}" ] && skopeo copy "docker://${IMAGE}:${{ inputs.tag }}" "docker://${IMAGE}:${{ inputs.extra_tag }}" --dest-creds "$CRED"
          DIGEST=$(skopeo inspect "docker://${IMAGE}:${{ inputs.tag }}" --format '{{.Digest}}' --creds "$CRED")
          echo "REF=${IMAGE}@${DIGEST}" >> "$GITHUB_ENV"

      # ⑤⑥ keyless 서명 + SBOM attestation + 검증
      - run: cosign sign --yes "${REF}"
      - run: cosign attest --yes --type spdxjson --predicate sbom/sbom-x86_64.spdx.json "${REF}"
      - run: |
          cosign verify "${REF}" \
            --certificate-identity-regexp "^https://github.com/${GITHUB_REPOSITORY}/.github/workflows/" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

트리거 워크플로 2개 (build.yml 호출만)

on: { schedule: [{ cron: "0 6 * * *" }], workflow_dispatch: {} }
# (날짜 stamp job 후) uses: ./.github/workflows/build.yml with { tag: latest, extra_tag: nightly-<date> }

5 바로 적용 체크리스트

  1. 레시피 배치 — 레포에 app-<lang>/, melange-<lang>.yaml, apko-<lang>.yaml, Makefile(APP 파라미터화)을 둔다. (이 레포가 그대로 템플릿)
  2. 워크플로 배치 — 위 build.yml / harden.yml / daily-rebuild.yml을 .github/workflows/에 넣는다.
  3. 권한 확인 — id-token: write + packages: write가 호출 job에 있는지. 이게 keyless 서명/푸시의 전제.
  4. 시크릿 0개 — GHCR push·서명 모두 자동 GITHUB_TOKEN + OIDC. 추가 PAT/키 불필요.
  5. push — git push → Actions harden 실행 → ghcr.io/<owner>/<repo>-{go,python,java} 생성·서명.
  6. 패키지 visibility — 첫 push 후 private로 생김. 조직 정책에 맞게 Package settings에서 조정.
  7. (선택) 배포 강제 — K8s에서 Kyverno/policy-controller로 위 서명 신원을 검증해 미서명 Pod 거부.

6 정직한 한계 — "마법"이 아닌 이유

한계의미 / 대응
앱 의존성은 별개trivy는 pip/jar 의존성도 스캔. 거기 CVE가 뜨면 rebuild로 안 사라짐 → requirements.txt/build.gradle를 패치버전으로 bump 필요
"0" = trivy/grype가 아는 0미공개·미탐지 취약점은 카운트 안 됨. "0 탐지"지 "0 존재"가 아님
--ignore-unfixed패치 없는 CVE는 게이트에서 제외(정책 선택). 끄면 Wolfi 패치 전까지 빌드가 막힘
HIGH/CRITICAL만 차단MEDIUM/LOW는 통과. severity 정책은 조직 기준에 맞게
시간 공백CVE 공개 → DB 반영 → 다음 daily 재빌드까지 최대 ~24h. 그리고 Wolfi가 패치한 경우에만 0 복귀

한 줄: 이 파이프라인은 OS·베이스 레이어의 CVE를 구조적으로 0으로 만들고, 매일 그 상태를 유지한다. 앱 자체 의존성의 CVE는 파이프라인이 탐지·차단하지만 고치는 건 당신 몫이다.
